## Post 2 — A Helpful AI App Still Needs Security Boundaries

**Suggested visual headline:**  
`AN AI MENTOR NEEDS GUARDRAILS TOO`

**Post copy:**

> 🧠 When I started building AetosAI Security Mentor, I did not want to make another generic chatbot.
>
> I wanted to make something that helps people think more clearly about secure AI behavior.
>
> That meant the app needed more than a good response box.
>
> It needed a way to help users ask better questions, practice against common AI security scenarios, and connect the answer back to real security guidance.
>
> So I built the experience around practical boundaries: 🛡️
>
> - Prompt-injection awareness
> - Safer agent and tool-use thinking
> - Security-first mentor rules and guardrails
> - Reference material from OWASP, MITRE ATLAS, and related frameworks
> - Evidence and audit views for review and follow-up
>
> I used **GitHub Copilot** throughout the build to help turn those ideas into working parts of the application. But Copilot was not the security decision-maker. Human judgment still mattered. 👤
>
> The security work was still about asking the right questions:
>
> What should this app do?  
> What should it refuse to do?  
> What needs a human review?  
> What evidence should be kept?
>
> That is the mindset I hope more analysts bring into AI projects. You do not need to know every framework before you begin. Build a small use case, learn where the boundaries are, and make the next version safer.
>
> Try the live app: https://aetosai.io 🔗
>
> What is the first guardrail you would add to an AI assistant that your team uses?

## Post 3 — Building the App Was Only Half the Job

**Suggested visual headline:**  
`SHIPPING SECURELY IS PART OF THE BUILD`

**Post copy:**

> ⚙️ Building the app was exciting.
>
> But I kept coming back to one question: how do I make sure I am not creating a security project with an insecure delivery process?
>
> So I treated the CI/CD pipeline as part of the product—not something to add at the end. 🔒
>
> AetosAI Security Mentor includes security checks in the delivery flow, including build validation, dependency checks, secret scanning with Gitleaks, and CodeQL analysis.
>
> The goal was not to pretend that one pipeline makes an app “perfectly secure.”
>
> The goal was to make security visible, repeatable, and easier to improve over time.
>
> I also used a phased approach: 📈
>
> 1. Observe what the checks find
> 2. Warn when the team needs to pay attention
> 3. Enforce the controls that are ready
> 4. Keep improving the evidence and process
>
> That is a lesson I am taking from this build: secure development is not one big finish line. It is a series of small, practical decisions that become part of how you ship.
>
> I built the application with help from **GitHub Copilot**, then added the CI/CD security controls so the project could keep learning after the first release.
>
> You can explore the live app here: https://aetosai.io 🔗
>
> If you are an analyst who wants to try building an app, pick one security problem you understand and build the smallest useful version. Then add one security check to the pipeline. That is a real start.
>
